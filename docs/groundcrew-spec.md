## 0. Confirmed Decisions & Guardrails (carry this into every prompt)

- **Audit-first gap analysis — architecture drift, backend reality, and why the build sequence had to be re-ordered**: The prototype and early planning language drifted from the actual implementation in several important ways. The clearest example was Warehouse: what looked like a simple front-end variant of a staff assignment model turned out to be a different operational architecture entirely, with legacy discrete Warehouse pages that encoded a route-based lead/member model rather than the unified stage-chain model ultimately required by the live event workflow. A second example was the confusion around `InventoryCrew` and `ProductionCrew`: early assumptions treated the WOM-side `ProductionManagerPage.tsx` / `InventoryOfficerPage.tsx` pages as if they were the same as the on-site Ground Crew roles of the same names. The actual codebase showed they were separate managerial layers with different semantics, and the Ground Crew roles had to be reconstructed as real event-scoped sub-roles with server-side claim resolution rather than imported from the WOM tree. The same audit also showed that a number of features that looked like “just needs wiring” were actually design gaps: the Admin configuration surface existed as a visible UI but had no storage model or enforcement path behind it; task-pool work needed a real backend entity instead of a UI-only queue; incident reporting was being routed into generic `audit_logs` rather than a first-class operational record; and damage-report stage tracking required additive schema work because the current table could not represent chain-of-custody stage or photo provenance precisely enough. The practical lesson is methodological rather than cosmetic: an audit-first, backend-inclusive process is essential before committing to a build sequence, because the frontend can display a plausible control, page, or role name while the actual architecture underneath it is different, missing, or non-authoritative. In thesis terms, this is a classic gap-analysis finding: the product had drifted into a different architecture than the prototype implied, and the cost of discovering this late would have been rework, false assumptions, and an invalid build sequence. The correct sequence therefore begins with role-model validation, backend claim alignment, and data-model verification before any feature is treated as a front-end-only wiring task.

- **Legacy Warehouse pages retirement and safe cutover plan**: `WarehouseLeadPage.tsx` / `WarehouseMemberPage.tsx` are confirmed for retirement once the replacement pure stage-based chain-of-custody flow in `GroundCrewPage.tsx` is confirmed working against real data after the Phase 3 backend read-access fix lands. The key verification finding is that the legacy pages are not backed by a dedicated server-side warehouse task or assignment entity: the repo scan found no persistent `WarehouseTask`/`WarehouseAssignment` table or historic warehouse-task record in the backend layer, and the actual page data source is the local mock store in `src/lib/warehouse.tsx` (`WarehouseEvent`, `WarehouseTask`, `CrewMember`, `ActivityEntry`, `ProductionJob`, `initialTasks`) rather than a canonical DB table. The real source of truth remains the canonical backend tables (`ManningAssignment`, `Event`, `Asset`, `Dispatch*`, `audit_logs`, `DamageReport`), so there is no real historical operational data to migrate from the old pages themselves. The safe cutover still requires the backend read-access fix, parallel parity verification, and a temporary fallback window before removal; the old pages are legacy UI shells, not canonical data, and they should not be treated as the source of truth during retirement.

**Role architecture — resolved after a two-round frontend audit plus the shift-lead reconciliation, treat as settled:**
- **Exactly 5 Ground Crew sub-roles.** `WarehouseCrew`, `FieldCrew`, `InventoryCrew`, `ProductionCrew`, `EventAdmin`. There is no account-level "Lead" role for any sub-role.
- **Inventory and Production are genuinely new Ground Crew sub-roles; do not reference or consolidate with `ProductionManagerPage.tsx` / `InventoryOfficerPage.tsx`.** They are separate WOM-management layers, not a shared Ground Crew permission model. The frontend must add explicit entries to `src/lib/rbac.ts`'s `GROUND_CREW_TREE_SEED` (e.g. `inventory-crew`, `production-crew`) and expose them in `AdminRolesPage.tsx` as live leaf roles with matching permission configuration. The backend must resolve the same canonical sub-role identities in `JwtService.cs` and `EphemeralClaimsTransformation.cs` from the user's effective `ManningAssignment.RoleName`/role mapping, emitting claims such as `GroundCrew_Inventory` / `GroundCrew_Production` alongside the base `Ground Crew` claim. The claim IDs must mirror the frontend tree exactly so the UI and API can't drift apart.
- **Shift-lead claim shape and authority model — resolved**: choose the explicit per-sub-role claim pattern for the only two shift-lead tiers: `GroundCrew_WarehouseShiftLead` and `GroundCrew_FieldShiftLead`. A single flat `GroundCrew_IsShiftLead=true` is explicitly rejected because it cannot distinguish whether the authority is for Warehouse Stage 1/4 or Field Stage 2/3, and a `FieldCrew` lead is not interchangeable with a `WarehouseCrew` lead. Inventory, Production, and Event Admin do not receive a shift-lead claim because they do not participate in the shift-lead tier. This claim is a UI convenience only, not an authorization source: the server-side stage-transition check remains a fresh `ManningAssignment` lookup on the actual dispatch route, using the active event/shift-date row and the demote-then-promote audit model. The live backend route today is `POST /api/dispatch/asset/{assetId}/status`; there is no live `POST /api/dispatch/event/{id}/status` route, and any future event-scoped transition endpoint must enforce the same check rather than trusting JWT claim data alone. Claims are refreshed only at login, so a live demotion, promotion, or date rollover must be reflected by the DB-backed authorization check rather than by trusting stale JWT data. Trusting the claim for a `403`-relevant decision would be a security regression and is explicitly not allowed.
- **Task creation toggle interacts with the shared task pool by entry state, not by a separate queue**: when `GroundCrewConfig` enables crew task creation, it does **not** create a parallel task model. Crew-created work enters the same `GroundCrewTaskPoolItem` pool as Manning-created work, but each row carries a `CreatedBy`/`Source` marker (`Manning` vs `Crew`) and an approval state such as `PendingReview` for crew-authored tasks. The creator can see the task immediately, but other crew members should not see it as an actionable ready-to-claim item until a Team Lead or Manning user approves or reclassifies it. The visual treatment is a distinct badge — **"Crew-created"** or **"Pending review"** — so the queue remains one system while the trust state differs. This preserves a single source of truth for the task pool and avoids a second approval queue that would drift from the canonical operational view.
- **Crew-created task approval authority / notification / staleness — resolved**: the approver for `PendingReview` crew-created tasks is **`EventAdmin`**, not the active Shift Lead, Manning, or a generic Admin override. This is the correct scope because `EventAdmin` was explicitly bounded to **event-scoped confirmation authority** earlier, while broader override powers were deliberately rejected; a crew task approval is a confirmation gate on the event's task pool, not a stage-by-stage operational override. The approver does **not** get a new standalone cross-event Pending Actions inbox as part of this decision. The intended mechanism is an **event-scoped signal** within the relevant event (for example, a count/badge or inline alert on the event's task-pool section within Event Detail), not a new `EventAdmin` home screen or general admin inbox. This keeps the role's footprint narrow and consistent with the repo's existing `EventAdmin` scope (`Home` summary + `Event Detail` event review), while still giving the approver a visible cue that an approval is waiting. If a crew-created task remains in `PendingReview` without any approval action, it should **stay pending indefinitely by default**; there is no auto-expire or forced escalation in the initial policy. The system may later add an aging/reminder pattern for visibility if product needs it, but the baseline decision is "no auto-aging" because the feature is a lightweight confirmation gate rather than a hard operational escalation. This keeps the workflow predictable and avoids creating a second escalation mechanism for a normal task-quality review path.
- **Thesis chapter framing — System Design — Ground Crew Mobile Module**: this section should be structured around four design pillars: (1) role/sub-role rationale, explaining why the module uses five fixed Ground Crew sub-roles instead of a flat account model and why `InventoryCrew` and `ProductionCrew` are distinct on-site roles rather than repurposed WOM management pages requiring both frontend RBAC configuration and backend claim resolution; (2) **two operational models: sequential authority vs. claimable work** — Warehouse/Field follow a stage-gated sequential model anchored to `ManningAssignment.IsShiftLead` on the active shift-date row, while Inventory/Production/EventAdmin follow a claimable work-item model based on `GroundCrewTaskPoolItem`; this split exists because the operational rhythms and authority patterns are fundamentally different, so a single unified task structure would misrepresent both domains; (3) chain-of-custody stage design, using the confirmed workflow `Dispatch → Arrival on Venue → Egress → Arrival on Warehouse` and showing how shift-lead gating, off-shift states, and the overnight grace window create a disciplined operational flow around authority and accountability; and (4) warning/escalation accountability, showing how the system combines policy configuration, warning logs, escalation flags, and audit trails so that one warning does not block operational work but still creates a traceable record for HR/management follow-up. The Manning-created vs. Crew-created provenance discussion belongs as a short task-pool-internal detail under the claimable-work model, not as part of the model-level comparison itself. This chapter should treat the module as a permissioned, event-scoped operational system rather than a generic PWA; the design objective is to enforce authority at the right layer (database-backed authorization for stage transitions) while keeping UI conveniences and informational banners separate from actual access control.
- **Thesis defense justifications (design decisions, short academic rationale)**:
  1. **Minimum of 1 Team Lead per sub-role — corrected scope**: The finalized, live requirement is not a blanket "one Team Lead per sub-role" rule across all five Ground Crew roles. For `WarehouseCrew` and `FieldCrew`, the operative rule is **at least one active `IsShiftLead` on the current shift-date** for the stage-gated operational path; if that lead is missing, the staffing-gap states block stage transitions. For `InventoryCrew`, `ProductionCrew`, and `EventAdmin`, there is no live shift-lead gating and no current requirement to maintain a Team Lead quota under the `IsShiftLead` model. The earlier "Number of Team Leads allowed: 0/1/2" configuration is a legacy admin quota artifact that should not be defended as live doctrine in the current architecture.
  2. **Separate task pool vs. chain-of-custody models**: The system separates sequential stage authority from claimable work because they are not the same kind of operation. Warehouse and Field are governed by state transitions with a single active authority path, whereas Inventory, Production, and EventAdmin are operational work queues with discrete items, meaning a single model would flatten materially different accountability patterns and misrepresent who is authorized to act.
  3. **15-minute default edit window after dispatch settlement (status: not live / not code-backed)**: No implementation or persisted config for `EditWindowMinutes` was found in the current codebase. The value remains a design option or future policy, not a verified live rule in the frontend or API. It should be treated as a proposed governance boundary until the backend config entity and enforcement hooks are added.
  4. **48-hour Team Lead confirmation override rule (status: prototype SLA, not authoritative override)**: `src/lib/manning.ts` declares `LEAD_CONFIRM_SLA_HOURS = 48`, and the UI surfaces 48-hour warnings for pending lead confirmations and field declarations (`src/pages/GroundCrewPage.tsx`, `src/pages/ManningPage.tsx`, `src/lib/ground-crew-declarations.ts`). This is a real prototype-level escalation SLA in the current SPA, but it is not the same as a persisted Team Lead override authority or a backend-enforced `IsShiftLead` override model. It should be described as a current UI SLA / escalation window, not an established backend override rule.
  5. **Retiring legacy Warehouse Lead/Member discrete-task pages in favor of a unified chain-of-custody model matching Field**: This retirement is justified because the legacy page model encodes the wrong abstraction for warehouse operations. Field and Warehouse both operate through a shared event-state narrative rather than discrete task pages, so unifying them under a common chain-of-custody model reduces conceptual drift, aligns authority with actual event flow, and makes role behavior legible to users and auditors alike.
  6. **Building Inventory/Production as new backend-supported sub-roles instead of repurposing WOM managerial pages**: This design prevents role confusion between event execution and management administration. The same names may appear in both domains, but the operational semantics differ: on-site Ground Crew roles require live event permissions and backend claim resolution, whereas WOM pages are managerial dashboards. Treating them as the same role would collapse two distinct accountability structures into one.
  7. **Per-assignment IsShiftLead flag on ManningAssignment instead of a permanent account-level Lead role**: A per-assignment flag reflects how staffing actually rotates in live events. Leadership is not a fixed identity property of a user but an operational condition attached to a specific shift, date, and domain; therefore, the model must encode assignment-specific authority to mirror real event staffing, while also preserving auditability when a lead changes over time.
- **Legacy Team Lead quota setting — resolved as superseded**: The earlier admin config for "Number of Team Leads allowed: 0 / 1 / 2" still exists in the current codebase in `AdminRolesPage.tsx` and the RBAC quota model (`minTeamLeads` / `maxTeamLeads`), but it is not the current source of truth for operational authority. The live authority model is `ManningAssignment.IsShiftLead` plus the staffing-gap rule for Warehouse/Field stage transitions. For the current 5-sub-role architecture, that means the live operational requirement is: a valid active `IsShiftLead` for the relevant shift-date on Warehouse/Field; no equivalent live stage-lead requirement for Inventory/Production/EventAdmin, because they do not participate in the stage-gated authority model. This older quota setting should therefore be treated as legacy/admin-compatibility configuration, not as an active design principle to cite in future prompts or thesis writing.
- **Team Lead quota deprecation decision (Phase 2)**: In Phase 2, the legacy Team Lead quota selector is deliberately removed from the live admin surface rather than kept visible-but-disabled. The reason is that Phase 2 is the point where the authority model is being corrected to the per-shift-date `ManningAssignment.IsShiftLead` model, and leaving a stale quota control in place would continue to communicate a now-invalid rule. The replacement in the same admin panel is a passive explanatory note only: "Team Lead authority is assigned per shift-date via the event roster and `IsShiftLead`; legacy team-lead quotas are deprecated and no longer enforced." This is acceptable because Phase 3 introduces the actual gated Warehouse/Field UI, and Phase 4 is the first point at which a config-backed admin policy could be reintroduced if product wants one. In other words, Phase 2 means: remove the control and all live enforcement behavior entirely; do not keep the old selector visible as a read-only/disabled artifact. If audit continuity is needed, keep the legacy value only in a non-actionable note or backend/log history, not as an active control in the UI.
- **Event Admin can never be vacant**: an active event must retain at least one assigned `EventAdmin` at all times. This is enforced in `AdminRolesPage.tsx` by blocking any save/remove action that would leave the event with zero `EventAdmin` assignments. If the user attempts to remove or reassign the only tagged `EventAdmin` without first selecting a replacement, the form shows an inline validation error and disables the save or remove action until a valid replacement is chosen. If the user confirms a replacement, the operation is treated as a two-step reassignment: select the replacement, confirm the swap in a modal, then commit both updates atomically. No save is allowed that transitions the event momentarily or permanently to zero admins. This is a hard business rule, not a soft warning.
- **Active stage-transition authority is per-shift-date, not per-event and not per-account.** `WarehouseCrew` gets active Stage 1/4 controls, and `FieldCrew` gets active Stage 2/3 controls, only when `ManningAssignment.IsShiftLead == true` on the row matching the *current effective shift date* (see grace window below) — resolved fresh each day, not once per event. Badges render dynamically: `{DOMAIN} • SHIFT LEAD` vs `{DOMAIN} • CREW`, or `OFF-SHIFT • NOT ROSTERED TODAY (date)` if no assignment row exists for today (stepper fully read-only in that state; damage/incident filing stays active regardless).
- **Shift-lead uniqueness & reassignment**: exactly one active `IsShiftLead = true` row per `(SubRole, EventId, ShiftDate)`. No auto-demotion — reassignment is an explicit two-step manager action (demote outgoing, then promote incoming), each step audit-logged. Terminology standard going forward: describe scope as "per shift" / "per shift date," never "per event."
- **Zero-shift-lead staffing-gap rule**: if an event has **zero** `WarehouseCrew` rows with `IsShiftLead = true` for the active shift date, then **Warehouse Stage 1/4 execution is blocked** for that shift until a valid lead is assigned. Likewise, if there are **zero** `FieldCrew` rows with `IsShiftLead = true` for the active shift date, then **Field Stage 2/3 execution is blocked** for that shift until a valid lead is assigned. This is a same-day staffing gap, not an absent-TL scenario. It is surfaced to **all rostered crew on that event/stage** via a non-modal banner in the active Ground Crew shell, with Manning/Admin seeing an additional actionable `Assign shift lead now` affordance and rostered crew seeing an informational `No active shift lead for this stage` message. The chain-of-custody stepper remains read-only and all stage controls are hidden/disabled while the gap remains open. `DamageReport`/`IncidentReport` filing remains active for all crew members regardless of lead coverage — this rule applies only to authority-bearing stage transitions, not to reporting. Re-flagging a different assigned crew member as the shift lead is an explicit admin/Manning reassignment action: target user must already be assigned to the same `(EventId, ShiftDate)` and same sub-role, the old lead is demoted, the new lead is promoted, and both actions are audit-logged. Inventory, Production, and Event Admin are out of scope here — they do not participate in the shift-lead tier at all.
- **Off-shift vs. staffing-gap differentiation**: an **off-shift** state means the logged-in user has no `ManningAssignment` row at all for the active date — this is a normal, expected state and should be shown as `OFF-SHIFT • NOT ROSTERED TODAY (date)` with no operational alert. A **staffing gap** means the user is rostered but the event has no valid shift lead for that stage/date — this is a real operational exception and should be shown as a distinct banner with warning color, copy, and explicit action. The two states must never be visually indistinguishable: off-shift uses neutral slate styling, while the staffing gap uses amber/red warning styling and tells the viewer there is no active shift lead for the stage. This is visible to all rostered crew, not just Manning/Admin, because the locked stepper needs a clear explanation for why no one can act. Manning/Admin keep the extra assignment affordance; base crew receive informational copy only.
- **Overnight grace window (dynamic cutoff)**: an outgoing shift lead's authority extends past midnight, capped at `min(06:00 AM Asia/Manila, nextShift.ShiftStartTime)` — guarantees zero overlap between consecutive leads. The 6:00 AM ceiling is a hard, intentional limit (not auto-extended past it, to prevent unbounded stale authority). A resulting coverage gap (next shift starting after 6:00 AM) is handled by scheduling convention (schedule the incoming lead ≤ 5:45 AM after an overnight shift) as the primary defense, with manual Manning reschedule as the fallback if a gap occurs anyway — not by extending the outgoing lead's window further. `EphemeralPermission` was evaluated for gap coverage and ruled out — it grants authority via role-claim injection, a separate path from the `IsShiftLead` check the dispatch endpoint actually evaluates, so it wouldn't pass authorization there without a bespoke, separately-scoped integration.
- **Grace window applies only to `IsShiftLead`-gated stage transitions** (Warehouse Stage 1/4, Field Stage 2/3) — it has no bearing on damage/incident filing (always-on for all 5 sub-roles) and doesn't interact with `InventoryCrew`/`ProductionCrew`/`EventAdmin` at all, since none of them have shift-gated actions.
- **Production and Inventory are genuinely new Ground Crew sub-roles, built from scratch — NOT** the same as `ProductionManagerPage.tsx`/`InventoryOfficerPage.tsx`, which are a separate WOM managerial layer (confirmed via an explicit code comment in `App.tsx` and `rbac.ts`'s own `WOM_SUBROLES`/`GROUND_CREW_TREE_SEED` separation). Don't reference or consolidate with those two WOM pages. Neither ever had a Lead tier — the shift-lead flag applies only to Warehouse and Field.
- **`WarehouseLeadPage.tsx`/`WarehouseMemberPage.tsx` are confirmed retired.** Warehouse moves entirely inside the unified `GroundCrewPage.tsx` shell as pure stage-based chain-of-custody (Dispatch → Arrival on Venue → Egress → Arrival on Warehouse), matching Field, now gated by the `IsShiftLead` flag rather than by page/route. The two legacy pages get removed only once the replacement is confirmed working, not upfront.

**Warning & Escalation system (Section 7) — settled shape:**
